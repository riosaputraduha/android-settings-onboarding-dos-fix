# F-03 — Onboarding task manager accepts an unverified caller identity, allowing a zero-permission app to exhaust and crash a core uid-1000 process

| Field | Value |
|---|---|
| ID | F-03 |
| Severity | **MEDIUM** (local denial of service, no privilege escalation) |
| Component | `android.onboarding` task manager, host `com.android.settings` |
| Affected build | Android 17 userdebug, `emulator-5566`, SettingsGoogle 107 MB system_ext build |
| Caller privileges | zero permissions (uid 10xxx, no runtime or signature permission) |
| Status | reproducible |

## Summary

`IOnboardingTaskManager.startTask` authenticates the caller by comparing the *caller-supplied*
task token's `COMPONENT`/`NODE` values and by a package-name check. The Settings host accepts a
caller whose package is in its `setupwizard` allowlist, but the task state is created **before**
the token is resolved, so an unresolved token still allocates a per-token entry. The state maps in
`OnboardingTaskStateManager` are unbounded and are only cleared on `close()`. In addition, the
built-in `DiagnosisProviderTask` honours a caller-supplied `delayFor` duration with no upper bound,
so a single small call can park a task for a day.

Both vectors let a zero-permission app grow the privileged Settings process until ART aborts it.

## Root cause

1. `createAndInitTask` writes `Failure("Task cannot be found.")` into `taskStateManager` for a token
   that matches no registered node, keyed by the caller-supplied token identity
   (`COMPONENT` + `NODE_ID` strings). Nothing evicts entries per token.
2. `DiagnosisProviderTask.runTask` does `delay(delayFor.toMillis())` without a clamp or timeout.
3. The authorization check (package name / certificate) does not run before state allocation, and
   the package-name check accepts a self-declared identity on images where the allowlisted package
   is not installed.

## Reproduction

Two PoCs, both from a zero-permission app:

- Long-key heap saturation — [pocs/POC-A17-F03-MEMDOS](../../../pocs/POC-A17-F03-MEMDOS/)
  (1,000 calls with 200 KB `COMPONENT` values → 173 MB Java heap, PSS 227 MB, at the 192 MB growth
  limit).
- Unbounded `delayFor` — same PoC, `{delayFor="PT24H"}`; 25,000 calls in ~37 s reach the growth
  limit and the process dies:

```
FATAL EXCEPTION: binder:2403_7
Process: com.android.settings, PID: 2403
java.lang.OutOfMemoryError: Failed to allocate a 24 byte allocation
    with 19520 free bytes and 19KB until OOM, target footprint 201326592,
    growth limit 201326592
```

The system restarts Settings; the DoS is repeatable.

## Impact

Local, repeatable denial of service against a core system app running as uid 1000. No code
execution, no data disclosure, no privilege escalation: the platform restarts the process, so the
effect is temporary but can be sustained.

## Fix recommendation

- Enforce the caller certificate before any state is created; do not trust a package name.
- Do not persist state for a token that does not resolve to a registered node.
- Clamp `DiagnosisProviderTask.delayFor`, cap suspended tasks per caller, and bound the state maps
  (LRU/TTL); cap accepted `COMPONENT`/`NODE` length.
